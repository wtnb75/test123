# 縦画面レイアウト

## 概要

ウィンドウが縦長のとき、盤面を 6 列 × 8 行にし、視野を「幅 768 × 端末の縦横比に合わせた高さ」にする専用レイアウトを使う。スマホを縦に持って、画面いっぱいに遊べる。高さは端末の縦横比に従うので、縦に長い端末ほど、盤面の見える部分が広くなる（横画面より広い）。横長のとき（既定）は、`docs/spec.md` の 1024 × 768・8 列 × 6 行のまま。コアループは変えず、「縦持ちで遊べる」ように広げる。

## 操作仕様（追加・変更分）

なし。操作（ドラッグ、タップ、クリック、Space、矢印キー、端スクロール）の効き方と数値（`dragThresholdPx`、`scrollSpeed`、`edgeScrollZonePx`、`edgeScrollSpeed`）は、縦画面でも同じ。次の 2 点だけ、論理キャンバスの大きさに従って読み替える。

- 端スクロールの「画面の端」は、縦画面の論理キャンバス（幅 768 × 高さ `viewH`）の端。
- Space の照準位置（マウスカーソルがないとき）は、縦画面の視野の中央（384, `viewH` / 2）。画面中央の白い照準リングも同じ位置に出す。

## 画面・Scene構成（追加・変更分）

### レイアウトの選び方

- **向きの判定**: ウィンドウ（ブラウザの表示領域）の高さが幅より大きければ縦画面、そうでなければ（幅と高さが等しい正方形を含む）横画面。幅か高さが 0 以下または数値でない（起動直後の 0 × 0 など）ときは、横画面にする。
- **縦画面の高さ `viewH`**: 幅を `portraitViewW`（768）に固定し、ウィンドウの縦横比に合わせて、`viewH` = 四捨五入(`portraitViewW` × ウィンドウの高さ ÷ ウィンドウの幅) とする（四捨五入は、小数部がちょうど 0.5 のとき切り上げる）。ただし `portraitViewHMin`（1024）以上、`portraitViewHMax`（1792）以下に収める（範囲の外は、その端の値）。
  - ウィンドウが 3:4 より横に近い（`viewH` が 1024 未満になる）ときと、3:7 より縦に長い（`viewH` が 1792 を超える）ときは、論理キャンバスがウィンドウに収まる分だけ FIT で拡縮し、余白が残る。
- **いつ決めるか**: Title、Game、Result の各 Scene が始まるときに 1 回だけ判定し（向きと `viewH`）、その Scene が終わるまで変えない。
  - Scene の途中で端末を回したり、ウィンドウの形が変わったりしても、その Scene のレイアウトは作り直さない。論理サイズのまま FIT で拡縮して収める（余白は背景色）。
  - 次に始まる Scene（Game → Result、Result → Game の「もう一度」、Result → Title など）が、そのときのウィンドウの形で、向きと `viewH` を決める。
  - Game の 1 回のプレイは、始まったときのレイアウト（`viewH` を含む）のまま最後まで続く。穴、出ているもの、スクロール位置が、プレイ中に組み替わることはない。
- 前の Scene と論理サイズが変わったときは、Scene の開始時に論理キャンバスの大きさを切り替える（Scene 開始のフェードインは、横画面と同じ）。

### 縦画面のレイアウト

- キャンバスは幅 768 × 高さ `viewH` の論理サイズ（最小は 768 × 1024（3:4）、最大は 768 × 1792（3:7））。ウィンドウに FIT で拡縮し、余白は背景色で埋める。
- 盤面は 6 列 × 8 行（1920 × 2560）。穴は 48 個、間隔 `holeSpacing` 320px は横画面と同じ。穴 i（0 始まり、行優先）の中心は ( 160 + (i mod 6) × 320, 160 + floor(i / 6) × 320 )（`viewH` によらず同じ）。
- 開始時のスクロール位置は盤面の中央（視点の左上が (576, (2560 − `viewH`) / 2)）。
- スクロール範囲は盤面の外に出ない: 視点の左上は x が 0 〜 1152、y が 0 〜 (2560 − `viewH`)。
- 見える広さは 768 × `viewH`。盤面（1920 × 2560 = 4,915,200 px²）に対して見える割合は、`viewH` 1024 で 16.0%、1662 で約 26.0%、1792 で 28.0%。横画面（約 16%）より広くなりうる。
- 視野の中央は (384, `viewH` / 2)。照準リング、Space の既定の位置、「タイムアップ！」をここに置く。方向矢印は視野の端から `arrowMargin` 内側、ネコ叩きの赤い面は視野全体を覆う。
- **Title**: 縦に積む。ゲーム名を上部、一言説明と操作説明を中央、スタートボタンを下部に置く。文字は幅 768 に収まるように折り返す。縦方向の位置はキャンバスの高さに合わせ、すべてがキャンバスに収まる（上下の余白に偏りがなく、スマホで押しやすい位置にボタンがある）。
- **Game**: HUD は、スコアを左上、残り時間を右上（右寄せ。画面の端からの余白は `hudMargin`、横画面と同じ）に固定表示する。HUD の位置は `viewH` によらず同じ（上端）。
- **Result**: スコアを中央に大きく、その下に「もう一度」「タイトルへ」のボタンを縦に並べる（横画面と同じ並び）。縦方向の位置はキャンバスの高さに合わせ、すべてがキャンバスに収まる。ボタンは指で押しやすい大きさ。

### 横画面と共通のもの

- Scene の流れ、Game のフェーズ（playing／ending）、Pop の状態遷移、演出・UI のすべて（効果、長さ、描画順）は、横画面と同じ。
- 文字の大きさは、縦画面の論理サイズ（768 幅）で読める大きさにする（細部は実装裁量）。

### 純粋ロジックのレイアウト引数

盤面と視野の大きさ、列数・行数を読む純粋ロジック（穴の座標と近傍、スクロール範囲と開始位置、方向矢印、端スクロール、浮かぶ文字の位置調整、出現計画のコンボの近傍）は、レイアウトを引数で受け取る。縦画面のレイアウトは、`viewH` から作る。ウィンドウの幅と高さから、向きに応じたレイアウト（縦画面なら上のとおり `viewH` を求めたもの、横画面なら 1024 × 768・8 × 6）を返す関数を、純粋ロジックにする。引数を省略したときは横画面になる（既存の呼び出しと単体テストを書き換えない）。

## ルール

- 規則（スコア、出現の間隔と同時数と割合、コンボ、おとり、当たり判定、予兆と出ている時間、矢印の対象と見た目）は、すべて横画面と同じ。
- 縦画面のコンボの近傍は、6 列の盤面で数える。盤面の端の穴（右端の列）の近傍に、次の行の左端の列の穴は含まれない。盤面の外の穴は選ばない。
- 方向矢印は、縦画面の視野（768 × `viewH`）に対して、横画面と同じ規則（`arrowMargin` だけ内側の長方形に切り詰める）で出す。
- 見える盤面の広さは `viewH` で変わる（縦に長い端末ほど広い）。このことは、ルールや数値の変更ではなく、画面の大きさの違いとして受け入れる。難しさの調整が必要なら `game-balance` で行う。

## パラメータ表

縦画面で値が変わるものだけ。それ以外の数値は、`docs/spec.md` のパラメータ表のとおり、横画面と同じ。

| 名前 | 縦画面の値 | 意味 |
|---|---|---|
| portraitViewW | 768 | 縦画面の論理キャンバスの幅（横画面の viewW は 1024） |
| portraitViewHMin | 1024 | 縦画面の論理キャンバスの高さの最小（3:4。ほぼ正方形のウィンドウはこの高さ） |
| portraitViewHMax | 1792 | 縦画面の論理キャンバスの高さの最大（3:7。これより縦に長いウィンドウは余白が残る） |
| boardCols × boardRows | 6 × 8 | 縦画面の穴の数（48 個。横画面は 8 × 6） |
| 盤面の大きさ | 1920 × 2560 | `holeSpacing` 320 のまま。横画面は 2560 × 1920 |

## テスト観点

レイアウトを引数に取る純粋ロジックについて、次のケースを単体テストにする。値は手計算。

- **向きの判定**: 幅 390・高さ 844 → 縦画面、幅 844・高さ 390 → 横画面。幅 800・高さ 800（等しい）→ 横画面。幅 800・高さ 801 → 縦画面（高さがちょうど 1 大きいと縦）。
- **縦画面の高さ `viewH`**: 幅 390・高さ 844 → 768 × 844 ÷ 390 = 1662.03 → 1662。幅 600・高さ 900 → 1152。幅 600・高さ 800（ちょうど 3:4）→ 1024。幅 600・高さ 801 → 1025.28 → 1025。幅 800・高さ 1000 → 960 は最小未満なので 1024。幅 800・高さ 801 → 768.96 → 769 は最小未満なので 1024。幅 300・高さ 700（ちょうど 3:7）→ 1792。幅 300・高さ 699 → 1789.44 → 1789。幅 300・高さ 701 → 1794.56 は最大を超えるので 1792。幅 390・高さ 1000 → 1969.2 は最大を超えるので 1792。小数部がちょうど 0.5 のとき切り上げる: 幅 1536・高さ 2049 → 768 × 2049 ÷ 1536 = 1024.5 → 1025（切り捨てなら 1024 になる）。
- **向きの判定の不正な値**: 幅 0・高さ 0 → 横画面、幅 0・高さ 844 → 横画面、高さ 0 → 横画面、幅か高さが数値でない（NaN）→ 横画面。
- **縦画面のレイアウトの中身**: `viewH` 1662 のとき、幅 768・高さ 1662・6 列・8 行・盤面 1920 × 2560。
- **縦画面の穴の座標**（`viewH` によらない）: 0 番 → (160, 160)、5 番（1 行目の右端）→ (1760, 160)、6 番（2 行目の先頭）→ (160, 480)、47 番（最後）→ (1760, 2400)。
- **縦画面のスクロール範囲と開始位置**: `viewH` 1024 → 右下を超える (9999, 9999) は (1152, 1536) に収まり、開始位置は (576, 768)。`viewH` 1662 → (9999, 9999) は (1152, 898)、開始位置は (576, 449)、左上を超える (−5, −5) は (0, 0)。`viewH` 1792 → (9999, 9999) は (1152, 768)、開始位置は (576, 384)。
- **縦画面の近傍**: 5 番（右上の隅）→ {4, 10, 11}（6 番は含まない。次の行へ回り込まない）、6 番（2 行目の左端）→ {0, 1, 7, 12, 13}、47 番（右下の隅）→ {40, 41, 46}、7 番（内側）→ 8 個。近傍は `viewH` によらない。
- **縦画面のコンボ**: 乱数を固定したとき、基点が 5 番なら選ばれる近傍は {4, 10, 11} の中だけで、6 番を選ばない。使用中の穴と盤面の外を選ばない。`viewH` によらず同じ結果。
- **縦画面の方向矢印**（`viewH` 1662）: 視野 { x: 500, y: 609, 幅 768, 高さ 1662 }（中央は (884, 1440)）で、穴の中心が (1760, 1440)（盤面の右の列の穴、真右）→ 位置 (728, 831)・向き 0。(884, 160)（視野の真上にある点。関数の例で、実在の穴の位置でなくてよい）→ 位置 (384, 40)・向き −π/2。視野の中の点は矢印なし。
- **縦画面の端スクロール**（`viewH` 1662）: カーソルが x = 768 → +1、x = 678 → 0（帯の内側の境界）、x = 723 → +0.5。y = 1662 → +1、y = 1572 → 0、y = 1617 → +0.5。帯の外は 0。`viewH` 1024 のときは、y = 1024 → +1、y = 934 → 0。
- **縦画面の浮かぶ文字の位置**（画面 768 × 1662、文字 100 × 40）: x = 0 → 74、x = 768 → 694、y = 0 → 114、y = 1662 → 1618。中央の点は動かさない。`viewH` 1024 のときは y = 1024 → 980。
- **見える割合**: 768 × `viewH` ÷ (1920 × 2560): `viewH` 1024 → 0.16、1662 → 約 0.2597、1792 → 0.28。
- **回帰（横画面）**: レイアウトを省略した呼び出し、および横画面を指定した呼び出しが、今までと同じ結果を返す。既存の単体テスト（出現、コンボ、矢印、スクロール、端スクロール、穴の座標、浮かぶ文字）が書き換えなしでそのまま通る。
- **回帰（規則）**: 縦画面でも、出現計画の乱数を引く回数と順序、おとりの抽選、叩きの判定、スコア、予兆と出ている時間の結果が、横画面と同じ（レイアウトが違っても、穴の選び方以外の結果が変わらない）。
- **Scene の接着部分の回帰**: 操作の効き方、矢印の見た目、演出は Scene の接着部分なので、単体テストではなく、ブラウザ QA（横画面のシナリオが前回と同じ結果であること）と、書き換えていない既存のテストで確認する。

## 完了条件

- 縦画面の確認は、単体ビルドと共有ビルドの両方で行う。
- 縦長の画面（スマホ縦 390 × 844 など）で、Title → Game → Result → Game（もう一度）、Result → Title の遷移ができ、盤面・HUD・矢印・照準リング・浮かぶ文字・「タイムアップ！」が論理キャンバス（768 × `viewH`）に収まって読める（スクリーンショットで確認）。盤面は 6 列 × 8 行で、穴は 48 個。
- スマホ縦（390 × 844）で、論理キャンバスが画面いっぱいに広がり、上下の余白が（ほぼ）ない（`viewH` 1662。スクリーンショットで確認）。
- 縦画面で、タッチ（ドラッグ＋タップ）・マウス（ドラッグ＋クリック、端スクロール）・キーボード（矢印キー＋Space）のそれぞれで、スクロールして叩ける（ブラウザ QA で操作して確認）。
- 向きと `viewH` は Scene の開始時に決まる: Game の途中でビューポートの形を変えても、盤面・穴・スクロール位置が組み替わらず、同じレイアウトのまま拡縮する。次の Scene（Result、リトライ後の Game）から新しい形になる（ブラウザ QA で確認）。
- 横長の画面（PC、スマホ横）では、いまの 1024 × 768・8 列 × 6 行のまま（スクリーンショットと既存の単体テスト）。
- 縦画面の追加で、次は変わらない（回帰条件）:
  - 横画面の動作と見た目（既存の単体テストがそのまま通ること、ブラウザ QA の操作確認が前回と同じ結果であること）。
  - ルール、スコア（+10／−20／0 未満にならない）、出現（間隔、同時数、ネコの割合、コンボ、おとり）、当たり判定、予兆と出ている時間。
  - 操作の効き方。
  - 方向矢印の規則と見た目、すべての演出。
- 縦画面で見える盤面の広さが、端末の縦横比で変わる（`viewH` 1024 のとき横画面と同じ約 16%、縦に長い端末ほど広い）。これは意図した違いで、回帰条件には含めない。
- README.md に、縦持ちでも遊べることと、縦持ちでは画面の高さに合わせて盤面が縦に広がることが書かれている。

## 実装裁量

- Title の説明文の折り返し位置とフォントサイズ（768 幅で読める大きさ）、Title と Result の縦方向の位置（キャンバスの高さに合わせ、すべてキャンバスに収まり、並び順と見た目を変えないこと）。
- 向きと `viewH` の判定に使う値の取り方（ウィンドウの内側の幅と高さ、または Phaser の親要素の大きさ）。
- 論理キャンバスの大きさを Scene の開始時に切り替える方法（Phaser の標準機能を使う）。
- レイアウトを表す型・引数の形、ファイル構成、既定値の持たせ方（省略時が横画面であること、が条件）。
- 縦画面の余白（FIT の外側）は背景色で塗る。何も表示しない。
