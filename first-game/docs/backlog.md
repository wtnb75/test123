# first-game 拡張候補（backlog）

公開済みの first-game（Minefield Rogue）に、次に足せるものの候補を、上から順に並べたものです。上のカードが「次の候補」です。仕様（`spec.md`）ではありません。`game-extend` が上から順に 1 件を選び、目的・コアループへの効き方・変えないものを固めてから、仕様に書きます。

- 規模: S = 1 画面と数値の追加程度、M = 複数の画面や仕組みにまたがる追加、L = 大きいので、`game-extend` で 1 PR 分に切り出してから採用する。

### HUD の操作ヒントを短く、入力に合わせて出し分ける（`hud-compact`）

- 狙い: HUD の 2 行目（メッセージ + 操作ヒント）は、14 px の等幅 1 行で折り返さず、メッセージを除いても約 85 文字（約 700 px）になる。幅 390 / 320 px のスマホでは右が切れ、死亡時の日本語の長い案内は 1280 px の画面でも切れる。タッチ操作でも「Move: arrows/QWEA-XZDC/numpad…」のキーの説明が出る。根拠: QA のスクリーンショット（390x844・320x568・1280x720）と `refreshHud` の文言
- 何を足すか: 操作ヒントを短くし、入力方法（キーボード / タッチ）で出し分ける。メッセージは 1 行に収めるか、2 行に分ける。死亡時の案内（R / T / 他のキー）は、ボタンの近くか短い文にする。
- コアループへの効き方: 広げない — 情報の読みやすさだけを直す。
- 種別: presentation-only
- 規模: S
- 出どころ: spec 分析（QA の画面）
- メモ: 同じ HUD を触る `hud-over-board` と続けて進めると効率が良い。文言は spec の実装裁量（HUD の 2 行目のメッセージ）。入力方法の判定（最後に使った入力で切り替える等）は `game-extend` で決める。

### HUD が盤面の下に隠れる（`hud-over-board`）

- 狙い: ドラッグでスクロールして盤面を上へ送ると、マスが左上の HUD（Stage / Score / High と操作ヒント）の位置に来て、文字が盤面に隠れ、文字の縁だけが白い点々のように残る。根拠: QA のスクリーンショット（ステージ 60、ドラッグ後）。入力の修正（`fix/first-game-input-robustness`）の変更ではなく既存の描画順
- 何を足すか: HUD の文字（`hudText` / `hintText`）と GOAL の矢印に、盤面より手前の描画順を付ける。または HUD の裏に帯を敷く。
- コアループへの効き方: 広げない — 情報の読みやすさだけを直す。
- 種別: presentation-only
- 規模: S
- 出どころ: QA
- メモ: 直すときは、STAGE ボタン・FLAG・ジョイスティック（depth 31 以上）との重なり順も確認する。盤面が HUD の位置にまで来ることを許すか、盤面の表示域を HUD の下に限るかは `game-extend` で決める。

### 操作ボタンを押しやすく、状態を分かりやすく（`controls-touch-size`）

- 狙い: STAGE ボタンは 90×34 px（コンパクト時 82×30）で、タッチの目安の 44 px に届かない。FLAG は 52 px（コンパクト 44）で、ON の見た目の差が小さい。仮想パッドは、つまみが動くだけで、どの 8 方向が選ばれたか、リピートが始まる前の 380 ms のタメが見えない。根拠: spec「ジョイスティックの大きさ」「STAGE」、`layoutVirtualControls` の定数
- 何を足すか: STAGE の大きさを 44 px 以上にする。FLAG ON のとき、ボタンとパッドの見た目をはっきり変える。パッドは選択中の方向のセクターを光らせる。
- コアループへの効き方: 広げない — 操作の分かりやすさだけを直す。
- 種別: presentation-only
- 規模: S
- 出どころ: spec 分析
- メモ: `tap-travel`・`touch-flag-chord` でパッドの役目が減る可能性があるので、パッドの見える化はその方針（パッドを残す）が決まってからでもよい。STAGE ボタンの位置は、HUD（右上）との重なりも確認する。

### マス・旗・プレイヤーを見分けやすく（`cell-contrast`）

- 狙い: 未開示のマス（`0x1e272e`）と背景（`0x0a1f2f`）、開示済み（`0x2f3542`）の色の差が小さい。旗は 16 px の「F」、プレイヤーは 12 px の「@」をマスの左上寄りに置いていて小さく、スマホでは読みにくい。根拠: QA のスクリーンショット（390x844・1280x720）と `BoardView` の寸法
- 何を足すか: 未開示・開示済み・背景のコントラストを広げる。旗を図形（三角の旗など）にする。プレイヤーを大きく、マスの中央に置く。色だけに頼らない（数字・記号を残す）。
- コアループへの効き方: 深める — 盤面の読み取りが速く確実になる（推理の入口）。
- 種別: presentation-only
- 規模: S〜M（`BoardView` の中身の変更。`render-cost` と同じ部品を触る）
- 出どころ: spec 分析（QA の画面）
- メモ: `Game` とタイトルのデモは同じ `BoardView` を使うので、デモの見た目も変わる。`render-cost`（描画の置き換え）と同時にやるか、先にどちらかを決める。

### 画面に合わせた盤面の拡縮と中央寄せ（`board-fit`）

- 狙い: 盤面は左上固定（原点 (20, 80)、1 マス 30 px）で、1280x720 のステージ 3（300 px 四方）は画面の左上 1/5 ほどで、右と下が空く。390 px 幅のスマホには 13 マス（ステージ 6）までしか収まらず、ステージ 7 以降はスクロールが要る。マスは 44 px の目安より小さく、タップを外すと即死する。根拠: QA のスクリーンショットと、幅 390 px・1 マス 30 px・左右の余白 20 px からの計算
- 何を足すか: 画面（HUD・パッド・ボタンを除いた領域）に収まる大きさに 1 マスを縮めるか、収まるなら中央に置く（下限・上限を決める）。収まらないステージは、これまでどおりスクロール。
- コアループへの効き方: 広げない — 盤面の見やすさ・押しやすさを直す。
- 種別: presentation-only
- 規模: M（カメラの追従・境界、タップのマスの座標変換、`BoardView` の原点と大きさに触れる）
- 出どころ: spec 分析（QA の画面・計算）
- メモ: `tap-travel` の前提（タップの的を大きくする）。1 マスの下限をどこにするか（読める数字の大きさ）と、ステージ番号が大きいときの扱いは `game-extend` で決める。`BoardView` は `cell` を引数に取れる作りになっている。

### タップで、開いたマスだけを通って自動で歩く（`tap-travel`）

- 狙い: 移動の入り口は、隣のマスのタップ（1 歩）とパッド（8 方向・リピート）だけで、開いた領域の中を離れた場所へ歩くには、何度もタップするかパッドを押し続ける必要がある。30 px のマスが隙間なく並ぶので、隣の 8 マスから狙った 1 マスを押し外すと、即死につながる。根拠: ユーザー（スマホで、スワイプやタップだけで操作できないか）、spec「盤面のタップ」「仮想パッド」、1 マス 30 px
- 何を足すか: 開いているマス（数字が見える・空白）で、プレイヤーから開いたマスだけを通って行けるマスをタップすると、そこまで 1 歩ずつ自動で歩く。未開示のマスは踏まない（開いたマスに爆弾は無いので、自動移動では死なない）。隣の未開示マスのタップは今までどおり 1 歩。歩いている間に、次の入力（タップ・キー・パッド）で止まる。
- コアループへの効き方: 広げる — 「開いた領域を歩く」手間を減らし、推理（どこへ踏み出すか）に集中させる。ルール・スコアは変えない。
- 種別: gameplay（操作）
- 規模: M（開いたマスの経路探索、自動移動の進行と中断、既存のタップ・パッドとの優先順位）
- 出どころ: ユーザー
- メモ: `board-fit`（マスを大きく）の後に置く。1 歩の間隔（`demoStepMs` と同じ 250 ms は遅いので、100 ms 前後）、止める入力、旗のマス・ゴールの扱いは `game-extend` で決める。経路探索は `core/` の純粋な関数にできる（タイトルのデモのボットと似ている）。

### 長押しでフラグ、自分のマスでコード操作。パッドを隠せるようにする（`touch-flag-chord`）

- 狙い: タップで移動できても、フラグを立てるには FLAG ボタンを ON にしてパッドの方向で操作し、コード操作はパッドのタップ（または S キー）が要る。パッドと FLAG が画面の下部を占め、タッチだけでは「パッドが必須」になっている。根拠: ユーザー（スマホで、スワイプやタップだけで操作できないか）、spec「FLAG ボタン」「コード操作」
- 何を足すか: 隣の未開示マスの長押し（例: 400 ms）でフラグの切り替え、自分のマスのタップでコード操作。仮想パッドと FLAG ボタンを、設定で隠せる（既定は表示のまま）。
- コアループへの効き方: 広げる — タッチだけで全ての操作ができる。ルール・スコアは変えない。
- 種別: gameplay（操作）
- 規模: S〜M（長押しとタップ・スクロールの判定の整理が中心）
- 出どころ: ユーザー
- メモ: `tap-travel` と合わせると、移動・フラグ・コード操作がタップだけで済む。長押しの時間・ドラッグ（スクロール）との区別・設定の保存先（隠す設定は localStorage に書くか）は `game-extend` で決める。誤タップの即死を防ぐ確認（ダブルタップなど）が要るかも検討する。

### STAGE の入力をゲーム内の UI にする（`stage-jump-dialog`）

- 狙い: 「STAGE」ボタンは `window.prompt`（ブラウザ標準の入力ダイアログ）で番号を入れる。スマホではキーボードが出て、ゲームの描画が止まり、見た目がゲームと合わない。根拠: spec「STAGE」、`promptAndStartStage`
- 何を足すか: 数字の入力を、ゲーム内の UI（± ボタンと確定、またはテンキー）にする。範囲（1〜`StageMax`）と拒否の表示はそのまま。
- コアループへの効き方: 広げない — 操作の見た目を整える。
- 種別: presentation-only
- 規模: M（入力 UI の新設、`prompt` に頼った検証・キャンセルの流れの置き換え）
- 出どころ: spec 分析
- メモ: STAGE ボタン自体が開発・確認向けの機能なので、公開の導線から外す案（URL の `?stage=` だけにする）もある。`game-extend` で、残すか外すかも決める。

### ゲームオーバーのボタンが画面の回転・リサイズで動かない（`restart-buttons-resize`）

- 狙い: ゲームオーバーの画面のボタン（RETRY / NEW GAME / TITLE）は、表示した時点の画面の大きさで位置が決まり、その後の画面の回転・リサイズで動かない。縦向きで死亡して横向きに回すと、下のボタン（TITLE）が画面の外になり、タッチだけの人は押せない。根拠: コードレビュー（`back-to-title` の 1 周目）。RETRY / NEW GAME は変更前から同じ挙動
- 何を足すか: `resize` のたびに、ボタンを新しい画面の大きさで置き直す（`restartButtonLayout` に新しい幅・高さを渡す）。
- コアループへの効き方: 広げない — 操作を失わないための修正。
- 種別: presentation-only
- 規模: S
- 出どころ: コードレビュー
- メモ: 「表示中に画面の大きさが変わっても動かない」と書いてある spec の一文を変える（`docs/spec.md` の死亡画面の節）。置き直しの規則（押し始めを受け付けた後に動いてよいか）も決める。

### 描画のコスト（`render-cost`）

- 狙い: マスごとに Container と Text を作り、ゴール・死亡のたびに盤面を作り直す。大きいステージではオブジェクトが数千〜数万になり、死亡時に引っかかり、スマホで fps が落ちる。根拠: コードレビュー（全体。ステージ 50 で約 6.5k、ステージ 100 で約 23k のオブジェクト）。未測定
- 何を足すか: マスを 1 つの Graphics か RenderTexture で描き、数字の Text は使い回す。変化したマスだけを更新する。
- コアループへの効き方: 深める — 大きい盤面でも、操作の応答が落ちない。
- 種別: presentation-only（見た目と挙動は変えない）
- 規模: M
- 出どころ: コードレビュー
- メモ: 盤面の描画は、`title-demo`（Title のデモ）で `Game` と `Title` の共有の描画部品に取り出し済み。ここでは、その部品の中身（マスごとの Container と Text）を置き換える。デモの盤面（最大 10×10）にも効く。

### 生成の信頼性（解決可能の保証を、大きいステージでも守る）（`generator-reliability`）

- 狙い: spec は「全ステージが推理だけで解ける」と保証するが、生成の上限（リトライ 1000 回・1500 ms）に達すると、解決可能かを見ずに「推理の深さが最大の候補」を使う。レビュアーがシード付きで測ったところ、ステージ 40 付近から保証が崩れ（ステージ 45 で 6 件中 0 件が解決可能）、生成が時間を超える（ステージ 200 で約 2.8 秒）。根拠: コードレビュー（全体）。測定はレビュアーのもので、未再現
- 何を足すか: 候補の選び方で、解決可能なものを優先する。時間の確認を試行の途中でも行う。制約伝播を、全盤面の走査の繰り返しではなく、変化した周りだけを見る形にする。ゴールまでの経路の解決可能性だけを見る案もある。
- コアループへの効き方: 深める — 「推理だけで必ず解ける」という約束を、進んだステージでも守る。
- 種別: gameplay
- 規模: L（生成と解決可能性の判定の仕組みを変える。測定のハーネスが先に要る）
- 出どころ: コードレビュー
- メモ: ステージ 40 以降まで遊ぶ人は少ない。先に再現と測定（ステージごとの解決可能な割合と生成時間）を、`core/` のテストの外のスクリプトで取る。シード付きの生成の結果が変わるので、既存のテストの期待値を見直す必要が出うる。
