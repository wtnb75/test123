# 盤面の描画

`docs/spec.md` の拡張。`Game` と `Title` のデモが共有する盤面の描画部品（マス・数字・旗・爆弾・マーカー・プレイヤーの印）の作り方を、大きいステージでも軽くなるものにする。見た目・ルール・操作は変えない（presentation-only）。

## 概要

いまの描画は、マスごとにコンテナ・四角・文字のオブジェクトを作り、ステージの開始・ゲームオーバーの色分けのたびに盤面全体を作り直す。ステージ 100（107 × 107 マス）では、ゲームオーバーの色分けの全体描画に約 300〜400 ms かかり、プレイ中の fps も落ちる。マスの四角をまとめて描き、文字は要るマスの分だけ持ち、変わったマスだけを更新することで、大きい盤面でも操作の応答が落ちないようにする（コアループの「推理して進む」の応答を保つ）。

## 操作仕様

変更なし（入力・カメラ・スクロールは `docs/spec.md` のとおり）。

## 画面・Scene構成

画面・Scene の構成と配置は変えない。変えるのは、盤面の描画部品の内側だけ。

- マスの四角は、マスごとのオブジェクトにせず、まとめて描く（1 つの `Graphics`、または `RenderTexture`。どちらにするかは実装裁量）。
- 数字・旗（F）・爆弾（\*）・誤った旗の「×」・確定爆弾の「!」・確定安全の「○」の文字は、マスごとに文字オブジェクト（`Text`）を作らない。見た目ごとに 1 つの見本を持ち、それが要るマスの分だけ、見本を使い回して表示する（要らなくなったら外す）。
- 重なり順（奥から）は変更前と同じ: マスの四角 → マスの文字 → スタート・ゴールのマーカー → プレイヤーの強調 → 「@」の印。盤面全体に同じ不透明度を掛ける（`setAlpha`。Title のデモのフェード）のも変えない。
- Scene の他のオブジェクトとの前後関係も変更前と同じ（盤面は、いまと同じく HUD の文字・GOAL の矢印の手前に描かれる。ドラッグでスクロールして盤面が HUD の位置に来ると、HUD の文字が盤面に隠れる、いまの挙動のまま。これを直すのは `docs/backlog.md` の `hud-over-board` で、この変更では変えない）。仮想パッド・FLAG・STAGE ボタン・結果のボタンより奥であることも同じ。
- 描画部品が `Game.ts` と `Title.ts` に見せる呼び出し（`render`・`renderChanged`・`updatePlayer`・`canDiff`・`setAlpha`・`setLayout`・`destroy`）は、呼び出す側のコードを変えずに使える形のままにする。`Game.ts` / `Title.ts` を変えてよいのは、呼び出しの最小限の修正だけ。

### 変わったマス（更新の単位）

- 「変わったマス」= 更新の前後で、マスの見た目の決定（下の純粋な関数）の結果が違うマス。手を進めたとき・フラグを立てたとき・コード操作のとき・ゲームオーバーの色分けのとき、変わったマスは**全て**更新する（古い色や文字を残さない）。変わっていないマスは触らない。
- 盤面全体の作り直しを許す場面: ステージの開始（ゴール後の次のステージ・RETRY・NEW GAME・STAGE のジャンプ・Title から `Game` を始めたとき）、盤面の大きさ・位置の変更（`setLayout` の後。画面の回転・リサイズ）、Title のデモのステージの差し替え。それ以外は差分で更新する。
- ゲームオーバーの色分けは、いまと同じく `render(stage, logical)` の呼び出しで描画部品に届く（`canDiff` / `renderChanged` を通らない）。描画部品は、自分が持っている前回の見た目と比べて、変わったマスだけを更新してよい。`Stage` の前後の比較は使えない（ゲームオーバーでは、爆弾を開示するために `Stage` の中身が直接書き換わるため）。盤面の大きさ・スタート・ゴールの位置が前の描画と違うときは、全体を作り直す（ステージ番号だけが違うときは、マスの見た目の差で更新する）。`canDiff` の契約は、これと矛盾しない範囲で実装が決める。

## ルール

- 見た目は変更前と画素まで同じ（マスの色・28 px の四角と 2 px の隙間・数字の色と縁取り・旗・爆弾・誤った旗の「×」とその色・ゲームオーバーの色分け・「!」「○」・マーカー・プレイヤーの強調と「@」の位置・重なり順）。Title のデモの縮小したセルでも同じ（文字は 8 px 未満にならず、寸法は 1 px 未満にならない）。
- ゲームのルール・生成・スコア・入力・HUD・各ボタン・数値は変えない。カメラは、スクロールの位置を整数の画素に丸める点だけを変える（奇数の画面幅でスクロールが半画素になると、マスの縁の画素が、図形で描いていた変更前と半画素ずれるため）。丸める箇所と方法: (a) 追従（`centerOn`）の直後に `Math.round`（0.5 は大きい側）で丸める（ステージの開始・画面の大きさの変更・回転の追従も同じ）。追従しない（追従のマージン内）ときは触らない。(b) ドラッグでは、ポインターの移動量を 1 画素単位で適用し、1 画素に満たない分は次の移動に繰り越す（ゆっくり小数の移動量で引いても、合計の分だけスクロールする）。境界（bounds）の制限は変えない（境界は整数なので、丸めて範囲外に出ない）。動くのは盤面と、スクロールに追従するもの（盤面の上のマーカー・プレイヤーの印・GOAL の矢印の位置の判定）が 0.5 画素以内。HUD・ボタン（スクロールに依らない物）は動かない。丸める以外のカメラの挙動（追従のマージン・スクロールの量・境界）は変えない。

## パラメータ表

| 名前 | 値 | 意味 |
|---|---|---|
| 死亡時の区間（`?stage=100`・ゲームオーバーの色分け） | 同じ計測の `?stage=30` の 1.3 倍以下 | 盤面の大きさに依存しないこと。変更前の実測（5 回の中央値）はステージ 30・50・100 で 65・116・405 ms（100 は 30 の 6.2 倍）、変更後の実測は 88・95・101 ms（1.15 倍）。絶対値で置かないのは、死亡直後に盤面の大きさに依存しない約 80 ms の 1 フレームがあり（ステージ 30 でも 100 でも同じ）、ソフトウェア GL の計測の床になるため。計測の条件は「完了条件」 |
| 呼び出し単体（`?stage=100`・ゲームオーバーの色分け） | 20 ms 以下 | 描画部品への呼び出し 1 回分の時間（`performance.now()` の差）。変更前の実測 294 ms、変更後の実測 10.7 ms（ステージ 30・50 は 2.7・4.8 ms） |
| fps の目標（プレイ中・ゲームオーバー中の `?stage=50`・`?stage=100`） | 同じ計測の `?stage=30` の 90% 以上 | 変更前の実測はプレイ中 60.5・60.5・46（ステージ 30・50・100）、ゲームオーバー中は単発の実測で 41・20・9.5。変更後の実測は、どちらも 60.5・60.5・60.5 |

## テスト観点

純粋なロジックの最低限のテスト対象（`Phaser` の描画そのもの・重なり順は QA のピクセル比較で確認する）。

- **マスの見た目の決定**（Phaser に依存しない純粋な関数）:
  - 入力: マスの状態（開示済みか・爆弾か・旗か・隣接の爆弾数 0〜8）、論理解析の分類（確定爆弾・確定安全・どちらでもない・解析なし）。
  - 出力: 背景色と、文字の並び（文字列・位置の種別（中央 / 左上）・色・太さ・基準セルでの大きさ・縁取りの色と太さ）。基準セル（30 px）の値で表にし、縮小は別の点（8 px の下限・1 px の下限）で確認する。
  - 表の取り方: 変更前の `createCellLayer` と `cellFillColor` が出した値を、変更前のコードから機械的に書き出す（characterization）。新しい実装から導いた値は使わない。
  - 行: ルールから起こりうる全ての組み合わせ（開示済み / 未開示 × 爆弾 / 安全 × 旗の有無 × 確定爆弾 / 確定安全 / どちらでもない / 解析なし）。起こりえない組み合わせを除くときは、その規則と理由を表の隣に書き、除いた数と残した数の和が全組み合わせの数と一致することを確認する。
- **変わったマスの集合**: 更新の前後の盤面から求めた「見た目の決定の結果が違うマス」と、更新したマスの集合が一致する（取りこぼし・余分がない）。手を進める・フラグ・コード操作（ゼロの自動展開を含む）・ゲームオーバーの色分けの各場合。
- **全体を作り直す場面**（純粋な関数 `sameBoardShape` と、マスの状態を作る `cellStateOf`）: 盤面の大きさ・スタート / ゴールの位置が変わるときは差分にならない。同じときは、ステージ番号が違っても、ゲームオーバーの色分けでも差分になる（見た目はマスの見た目の決定の結果の差で決まる）。

## 完了条件

- [ ] 盤面の描画が軽い。計測は使い捨ての計測用コード（コミットしない）で行う。条件: ヘッドレス Chromium（ソフトウェア GL）・390x844・`?stage=N` で開き Title から Enter で始める。区間: 死亡を確定させる手の結果を描画に反映する、描画部品への呼び出しの直前から、その結果を描いた最初のフレームが終わるまで（呼び出しの後の 2 回目の `requestAnimationFrame` のコールバックの時刻との差。`Graphics` にまとめる方式では、呼び出しは描画の命令を積むだけで、実際の描画は次のフレームに移るため、呼び出し単体の時間では測らない。`render` でも `renderChanged` でも、複数回呼ぶなら最初の呼び出しの直前から）。死亡させる手は、`window.__qa.bombs` のうち、プレイヤーに最も近い爆弾（距離は縦横の差の大きいほう）へ、方向キー（8 方向）で 1 歩ずつ近づいて踏む入力とする（全ステージで同じ選び方）。結果の表示は `window.__qa.phase === 'gameover'` で検出する。各ステージ（30・50・100）5 回の中央値が、区間は `?stage=100` が `?stage=30` の 1.3 倍以下、呼び出し単体（1 回の死亡で呼ぶ全ての呼び出しの合計）は `?stage=100` で 20 ms 以下。fps は、プレイ開始の 0.5 秒後から操作せずに 2 秒間（ゲームオーバー中は、結果が出てから 0.8 秒後から 2 秒間）の `requestAnimationFrame` の回数を数え（`scripts/qa/lib.mjs` の `fps`）、各ステージ 5 回の中央値を、同じセッションで測った `?stage=30` の値と比べる（`?stage=50`・`?stage=100` が 90% 以上）。実装後の実測値は上の表に書いてある（QA で測り直し、外れたら理由とともに報告する）
- [ ] 実機の確認。ヘッドレスのソフトウェア GL は実機の GPU の代理として弱いため、スマホなど実機で、ステージ 50 以上（`?stage=50`・`?stage=100`）で死亡したときに、引っかかりがなく（ステージ 100 は盤面だけで約 41 MB のテクスチャを使うため、メモリ不足の様子も見る）、ゲームオーバーの色分けがすぐ出ることを、ユーザーが確認する（`scripts/qa/share.sh` で URL を出す）。引っかかりが残る場合は、機種と体感を報告し、`docs/backlog.md` の次の候補（画面に見えているマスだけを描く）として進める。この変更の完了は妨げない
- [ ] 描画の見た目が変わっていない。QA: 乱数の元を固定する（`page.addInitScript` で `Date.now`（ステージ生成の既定のシード）を定数に、`Math.random`（Title のデモの既定の乱数）を種つきの乱数に差し替える。`performance.now` と `requestAnimationFrame` は触らない。`Date.now` が止まるので、生成の打ち切り（時間上限）が働かず、ステージ 50 の生成待ちは長くなる。待ちのタイムアウトを延ばす）。固定の結果、変更前の成果物と変更後の成果物で `window.__qa.bombs`（`Game` の開始後に読む）が同じ盤面になることを先に確かめる。実行ごとに新しいブラウザコンテキストを使う（保存されたハイスコア・開始ステージを持ち込まない）。画面の大きさは 390x844・375x550・667x310 の 3 つ。同じ入力の列（開始直後・方向キーで数手進める・フラグを安全なマスと爆弾のマスに立てる・ドラッグでスクロールして盤面が HUD の位置に重なる状態（ステージ 10 以上）・爆弾を踏んでゲームオーバー。確定爆弾・確定安全・誤った旗が画面に出る場面を 1 つ以上含む）を、各入力の 500 ms 後かつ `__qa` の `player` が 2 回続けて同じ位置になってから撮る。撮るのは HUD・ボタンを含む画面全体で、変更前の成果物（`origin/main` の `Game` に、上のカメラの位置の丸め（追従の直後の丸めと、ドラッグの 1 画素単位の適用）と同じ変更だけを足したもの）と変更後の成果物を、ステージ 1・10・50 でピクセル比較して、差が 0 画素である。Title のデモは、時間で進むので、ページを開いて Title が出た直後（デモの最初の盤面。`demoWaitMs` 未満で撮る）だけを比べる。手を進めた後の描画は `Game` の差分の更新の比較で確認する。差が出たら、差の場所を見て変更前と同じ画素になるように直す（許容しない）

## 実装裁量

- 四角を `Graphics` と `RenderTexture` のどちらにするか、文字の見本の共有のしかた（見本の `Text` の canvas を共有する `Image` を含む。数・外し方）、差分の求め方（`Game` が変わったマスを渡すか、描画部品が前回の見た目との差から求めるか）、内部のクラス・ファイルの分け方。
- 純粋な見た目の決定の関数の名前・型・置き場所（入力と出力の内容は「テスト観点」のとおり）。
- 画面に見えているマスだけを描く方式は、この変更の範囲外（目標に届かないときの次の候補として `docs/backlog.md` にある）。
