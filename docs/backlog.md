# リポジトリ全体の拡張候補（backlog）

複数のゲームにまたがる作業（共有パッケージ・トップページなど）の候補を、上から順に並べたものです。上のカードが「次の候補」です。仕様（`spec.md`）ではありません。1 つのゲームだけに閉じる候補は各ゲームの `docs/backlog.md` に、新しいゲームのアイデアは `docs/ideas.md` に書きます。

- 規模: S = 1 つのファイルや画面の追加程度、M = 複数のゲームや仕組みにまたがる追加、L = 大きいので、1 PR 分に切り出してから採用する。
- 1 つのカードは 1 つの目的にする（1 変更 1 目的）。
- 共有パッケージの置き方は AGENTS.md 2.1 節に従う（`shared/<name>`、使うすべてのゲームのテストを通す）。

### digdle の最高の連勝を保存する（`digdle-best-streak`）

- 狙い: digdle は、トップページに出せる「最高の記録」が無い。`digdle.stats` は挑戦数・勝ち数・今の連勝・試行数の合計だけで、連勝は負けると 0 に戻り、過去の最高値が残らない。`best-store` の約束（1 ゲーム 1 つの `{score, label}`）に載せる値が無く、トップページで digdle のカードだけ空になる。根拠: `digdle/src/game/logic/stats.ts`（`StatsEntry` に最高の連勝が無い）、`best-migrate` で digdle だけ移せなかったこと
- 何を足すか: 最高の連勝を保存し、`digdle.best` に `{score: 最高の連勝, label: "連勝 N"}` の形で書く。モードと桁数ごとに統計があるので、どの組の連勝を代表にするか（全体の最大か、既定のモードか）を `game-extend` で決める。日替わりの進行（`digdle.daily`）は記録ではなくセーブなので、触らない。
- コアループへの効き方: 広げる — 連勝を伸ばす理由が、統計の外（トップページ）にも見える。ルールは変えない。
- 種別: gameplay（保存する値が増える。判定・出題・ルールは変えない）
- 規模: S〜M
- 出どころ: ユーザー（`best-migrate` で digdle を対象から外したとき）
- メモ: トップページは記録が無いカードに何も出さない作りなので、digdle は空のまま動く（急がなくてよい）。日替わりを持つゲームがもう 1 本できたら、日替わりの共通部品を切り出すか考える（今は 1 本だけなので切り出さない）。`digdle.stats` の読み方・消し方（統計のリセット）は変えない。

### wordfall と typerain の自己ベストを共有の形に載せ替える（`best-migrate-labs`）

- 狙い: wordfall と typerain は、自前の `best.ts` で自己ベストを保存している。キーと値が別形式（`wordfall:best`・`typerain:best`、値は数値だけ）なので、トップページ（`labs.html` を含む）のベスト記録の表示に出ない。根拠: `wordfall/src/game/logic/best.ts`、`typerain/src/game/logic/best.ts`、`shared/best-store`
- 何を足すか: 2 本の保存を `shared/best-store` の約束（キー `<game-dir>.best`、値 `{score, label}`）に載せ替え、自前の `best.ts` を `BestStore` に置き換える。`label` は画面に出す文字列に合わせる（例: `BEST 1200` の数字の部分を含む短い文）。
- コアループへの効き方: 広げる — `labs.html` のカードにも自己ベストが見え、もう一度挑戦する理由になる。ゲームのルール・スコアの付け方は変えない。
- 種別: presentation-only（保存の形の変更）
- 規模: S〜M（2 ゲーム）
- 出どころ: ユーザー（ハイスコアが無い公開中のゲームの洗い出し）
- メモ: 以前のキー（`wordfall:best`・`typerain:best`）に残った記録は読まない・移行しない（先に載せ替えた 4 ゲームと同じ決め）。ゲームごとに 1 PR にする（1 ゲームの追加・修正は 1 PR）。両ゲームの spec の「保存」の記述（キー・形式）を先に更新する。`BEST ---`（記録なし）の表示や、新記録の通知は変えない。

### ハイスコアに達成日を付ける（`best-date`）

- 狙い: トップページのハイスコアは「いくつか」しか分からず、いつ出した記録か分からない。古い記録なのか最近の記録なのかで、もう一度挑戦する気持ちが変わる。根拠: ユーザーの声（ハイスコアには達成日も付けたい）、`shared/best-store`（保存の値は `{score, label}` だけ）
- 何を足すか: `shared/best-store` の保存の値に達成日（`date`）を足し、`record` が記録を更新したときに今日の日付を書く。トップページ（`scripts/build-index.mjs`）は、`label` の横に日付を出す。
- コアループへの効き方: 広げる — 記録が「いつのものか」まで見えて、更新する理由が増える。ゲームのルールは変えない。
- 種別: presentation-only（共有パッケージの保存の形の追加）
- 規模: S〜M
- 出どころ: ユーザー
- メモ: 決めること: (1) 日付の形（`YYYY-MM-DD` の文字列か、時刻の数値で保存して表示で整形するか）と、どのタイムゾーンの日付にするか（端末のローカル）。(2) `date` は省略可にする。`date` の無い既存の記録は、そのまま読めて、日付なしで表示する（`parseBest` を壊さない）。(3) 同点では更新しない約束（厳密に超えたときだけ）は変えないので、日付は「その記録を初めて出した日」になる。(4) 時刻は注入できるようにする（テストの再現性。AGENTS.md 4.5 節）。使う 4 ゲーム（bouncewave・pushline・calc1・first-game）のテストをすべて通す。トップページのスクリプトは `best-store` を import できないので、`readBestLabel` を日付も返す形に直し、`parseBest` と条件をそろえる。

### トップページからハイスコアを初期化する（`index-reset`）

- 狙い: 記録を消す手段が、ブラウザのサイトデータの削除しか無い。消すとほかのゲームの記録や設定まで失う。根拠: ユーザーの声（初期化ボタンを付けたい）
- 何を足すか: トップページに、ベスト記録を初期化するボタンを足す。確認の手順を挟み、消すのは `<game-dir>.best` のキーだけにする。
- コアループへの効き方: 広げない — 記録の管理だけ。
- 種別: presentation-only
- 規模: S
- 出どころ: ユーザー
- メモ: トップページのハイスコア表示（`scripts/build-index.mjs`）の後。ハイスコアではない保存（`kogodrop.records` の学習記録、`digdle.daily` の日替わりの進行、`minefield-rogue-pad` の設定）は消さない。元に戻せないので、全ゲーム一括か、ゲームごとかを決める。

### トップページで共有 Phaser を先読みする（`index-prefetch`）

- 狙い: 共有ビルドのゲームは、カードを押してから `../vendor/phaser-<version>.esm.min.js` を取りに行くので、初回の起動に取得待ちが入る。トップページにいる間に取っておけば、その待ちが減るかもしれない。根拠: ユーザーの案、`scaffold/vite/config.prod.mjs`（ゲーム側はすでに同じ URL へ `modulepreload` を張っている）
- 何を足すか: `scripts/build-index.mjs` が、共有 Phaser の URL（`vendor/phaser-<version>.esm.min.js`）に対する `<link rel="prefetch" as="script">` をトップページ（と `labs.html`）に出す。pnpm workspace の `catalog:` で Phaser のバージョンが 1 つに揃うので、先読みは 1 本で足りる。
- コアループへの効き方: 広げない — 読み込みの待ちだけ。ゲームの挙動は変えない。
- 種別: presentation-only
- 規模: S
- 出どころ: ユーザー
- メモ: **効果は未確認**（ユーザーも怪しいと見ている）。実装の前に、`task build` の `output/` をサブパスで配信し、DevTools で次の 3 点を確かめる。(1) ゲームの起動時に vendor がキャッシュから出るか（GitHub Pages の `Cache-Control` は短い）、(2) Safari（iPhone）でも `prefetch` が再利用されるか、(3) トップページ自体の表示を遅らせないか。効果が見えなければ見送る。優先度が高い `modulepreload` は使わず、低優先度の `prefetch` か、アイドル時・カードの hover / touchstart での取得にする。通信量を節約する設定（Save-Data）の端末は先読みしない。バージョンが複数に分かれた場合（`catalog:` を使わないゲームが出たとき）は、`output/vendor/` を列挙して対応を見直す。

### 記録をモードごとに持てるようにする（`best-store-modes`）

- 狙い: `best-store` の約束は 1 ゲーム 1 件（`<game-dir>.best`）で、モードごとにスコアが独立するゲームの記録を持てない。今そのゲームは無いが、モードのあるゲームは出てきそうなので、そのとき保存の形が各ゲームで別々になるのを防ぎたい。根拠: ユーザーの指摘（モードごとにスコアが独立するケースがありそう）、digdle（モード × 桁数の統計）
- 何を足すか: `shared/best-store` に、モード別の記録 `<game-dir>.best.<mode>`（同じ `{score, label}`）を足す。トップページに出す代表の 1 件は、これまでどおり `<game-dir>.best`。
- コアループへの効き方: 広げない — 保存の形だけ。
- 種別: presentation-only（共有パッケージの追加）
- 規模: S
- 出どころ: ユーザー
- メモ: **該当するゲームが出るまで採用しない**（先に足しても使う場所が無く、1 本分の形に合わせて作ると外れる）。足すときは、`BestStore` に `mode` を渡す形を、そのゲームの spec と一緒に決める。トップページは代表の 1 件だけを読めば足りる。
