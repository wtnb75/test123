# fukuwarai ゲーム仕様

## ゲーム名

**fukuwarai** ― 福笑い風パーツ配置ゲーム（仮称）

## コンセプト

福笑いのように、お題の元絵を見ながらパーツ（目・鼻・口など）をドラッグで配置し、仕上がりが元絵とどれだけ似ているかでスコアをつける。

## ターゲットプレイヤー

- スマホで気軽に遊べる隙間時間の暇つぶしを求める層

## コアループ

1. お題の元絵を画面全体に表示する（記憶を頼りに配置する、いわゆる福笑い形式）
2. プレイヤーが「はじめる」ボタン（仮称）をタップ／クリックすると元絵を隠し、パーツ配置フェーズに切り替わる。一度隠したら再表示はしない（MVP範囲）
3. パーツをドラッグで配置する。パーツはつかんだ場所がポインタに追従する形で位置と回転が同時に決まる。配置エリアで離すとその位置・角度で確定して以後動かせなくなり、トレイ領域で離すと確定せず、離した場所からやり直せる
4. プレイヤーが「採点する」ボタンを押すと、その時点の配置で採点する（全パーツを動かしたかどうかの自動判定はしない。トレイに残ったパーツはそのまま採点対象になり、結果的に低スコアに反映される）
5. 採点結果（点数と、プレイヤーが実際に並べた顔）を表示する
6. 次のお題へ進む（MVPでは1本道なのでリトライ／タイトルに戻る）

## 操作仕様

| 操作 | 方法 |
|------|------|
| パーツの配置＋回転 | パーツ上の好きな場所をつかんでドラッグする。つかんだ場所がそのままポインタに追従し、引っ張る位置・方向に応じて位置と回転が同時に決まる（例: 端の方をつかんで引っ張ると、その端がポインタについてくるように回転しながら移動する）。**配置エリア**（顔を組み立てる領域）で指／マウスを離すと、その位置・角度でパーツが確定し、以後そのパーツは操作できなくなる |
| パーツをトレイに戻す | 未確定のパーツを**トレイ領域**まで運んで離すと、確定せずその離した場所に留まり、再びそこからつかんで配置し直せる（初期のトレイ位置には戻らない） |

- 配置エリアで離した時点でそのパーツは確定し、以後動かせない（再配置不可）。トレイ領域で離した場合のみ確定せず、離した場所からいつでもやり直せる
- ドラッグ中は、パーツ上のどこを掴んだかが分かるよう、掴んだ点に小さな印（マーカー）を表示する。マーカーはパーツと一緒に追従・回転し、指／マウスを離すと消える
- 拡大縮小操作はなし
- PC（マウス）・スマホ（タッチ）の両方を常時受け付け、同じ操作感になるようにする

## 画面・Scene構成

| Scene | 役割 |
|-------|------|
| `Boot` | アセット読み込み |
| `Title` | タイトル画面、スタート導線 |
| `Game` | メインプレイ。内部に「元絵表示」「パーツ配置」「採点」の3フェーズを持ち、Scene自体は分割しない。パーツ配置フェーズの画面は「配置エリア（顔を組み立てる領域。輪郭は最初から描画済みで、以後変化しない）」と「トレイ領域（未確定パーツの置き場）」で構成する |
| `Result` | 採点結果表示。**プレイヤーが実際に並べた顔を画面中央に大きく表示**し（福笑いは出来上がった顔を見て笑うゲームなので、点数だけでなく仕上がりそのものを見せる）、正解の顔は比較用に小さく添える。点数とリトライ／タイトルへ戻る導線も表示する |

### レイアウト方針（縦長スマホ画面を基準、`Scale.FIT` + `CENTER_BOTH` でPC横長画面にも対応）

- 画面上部〜中央: 配置エリア（顔の輪郭を含む、パーツを組み立てるメインスペース）
- 画面下部: トレイ領域（未確定パーツを横一列に並べる帯状エリア）
- 「はじめる」ボタン: 元絵表示フェーズ中、画面下部中央に表示
- 「採点する」ボタン: パーツ配置フェーズ中、トレイ領域の下（画面最下部）に常設表示
- `Result` Scene: 画面中央〜上寄りにプレイヤーの仕上がり（大）、その脇か下に正解の顔（小、参考用）、点数はプレイヤーの仕上がりの近くに表示。画面下部に「もう一度」「タイトルへ」ボタン

## ルール（勝利条件・失敗条件・スコア条件）

- 勝敗の概念はない（タイムアタックやライフ制ではない）。元絵は最初に一度だけ表示され、プレイヤーの操作（「はじめる」ボタン）で隠れたあとは再表示しない。「採点する」ボタンをプレイヤーが押した時点の配置で採点フェーズに進む
- スコアは、プレイヤーが配置した結果（輪郭を除く6パーツ）と、正解パラメータ（各パーツの正しい位置・回転角）から同じ描画ロジックで生成した「お手本」を、それぞれオフスクリーンに描画して比較したピクセル単位の差分から算出する類似度（0〜100点）とする。お手本・プレイヤー結果のどちらもラスター画像アセットではなく、実行時に `Phaser.Graphics` 等で描画したものを比較する（技術要件を参照）
  - 実装方針: プレイヤー配置・お手本の双方を同じ解像度・同じ背景色（白）のオフスクリーンに描画 → 対応する各ピクセルについて、**両方とも背景色のピクセルは比較から除外**し、それ以外（どちらか一方でも背景色でないピクセル）のみRGB各チャンネルの差の絶対値を合計する → 対象ピクセル数×3（チャンネル数）で割って平均差分（0〜255）を求める（この値を `実差分` とする）
  - 背景除外の理由: 背景全体を含めて平均を取ると、顔の絵が比較キャンバスのごく一部しか占めないため、パーツを何も配置しなくても「背景同士が一致している」ことで高スコアが出てしまう。背景ピクセルを比較から除外することで、実際に絵が描かれている領域の一致度だけをスコアに反映する
  - **点数への変換（`何もしない=0点` 基準の按分）**: 単純に `100 * (1 - 実差分 / 255)` で線形変換すると、パーツの配色が背景（白）からそれほど離れていないため（特に目は塗りが白で背景と同色になり採点からほぼ除外される）、何も配置しなくても40点前後出てしまうことが実測で分かった。これでは「頑張って正確に置く」動機が弱まるため、**「何もパーツを配置しない状態（トレイのまま、キャンバス上に何も描かれていない状態）とお手本を比較したときの差分」を `基準差分` とし、それを0点、差分0（完全一致）を100点として按分する**方式に変更する:
    - `score = 100 * (1 - 実差分 / 基準差分)`（0〜100の範囲にクランプする。`実差分` が `基準差分` を上回った場合＝背景のまま何もしないより悪い配置になった場合は0点）
    - `基準差分` はお題ごとの正解パラメータ・配色から決まる値なので、ハードコードした定数にせず、採点のたびに「背景のみ（パーツなし）のキャンバス」と「お手本」を同じ比較関数で計算して都度求める（パーツの配色やお題を将来増やしても自動的に追従させるため）
  - **位置ズレへの許容度（`game-balance` での調整）**: 実測（回転誤差を2°以内に抑えたまま、位置だけを意図的にずらして採点）で、位置ズレ0pxで91点だったのに対し、わずか3pxのズレで64点（-27点）、6pxで49点（-15点）と、ズレの初期数pxでスコアが急落する「崖」状のカーブになっていることが分かった。目・眉のような小さいパーツは数pxのズレで正解パーツとの重なりがほぼ消え、重ならない領域が「配色 vs 白背景」の最大差分に近い値になるため、平均差分が急上昇するのが原因。実際の指/マウス操作でこの精度（3px以内）を安定して出すのは難しく、「感覚的にはほぼ正確に置けた」のにスコアが伸びない体験になりやすいと判断し、**採点用オフスクリーン描画に軽いぼかし（ガウシアンブラー相当）を適用してから差分計算する**ことで、数px単位のズレへの許容度を上げる（技術要件のスコア計算部分を参照。ぼかし半径は実測して決める）

## MVP範囲

- お題（顔の元絵とパーツ一式）は1種類のみ
- 輪郭は配置エリアに最初から描画されている背景要素とし、ドラッグ対象のパーツには含めない。ドラッグで配置するパーツは「眉2・目2・鼻1・口1」の計6パーツで固定
- ステージは1本道（お題選択なし）
- 元絵は「はじめる」ボタンを押すまで表示し続け、押したら隠れて以後再表示しない
- 採点は「採点する」ボタンをプレイヤーが押したタイミングで実行する（全パーツ移動の自動検知はしない）
- スコアは配置後画像とお手本のピクセル差分（技術要件・ルール参照）で算出。輪郭は両者で常に同一のため採点対象から除外する
- パーツは初期状態でトレイ領域に置かれている。ドラッグして配置エリアで離すと位置・回転が確定し以後操作不可（再配置不可）。トレイ領域で離した場合は確定せず、離した場所に留まり何度でもやり直せる
- ドラッグ中のパーツは最前面に表示する（パーツ同士の重なりは許容する）

## 非MVP範囲

- 複数のお題セット、およびお題のランダム選出
- SSIM等、より精密な画像類似度アルゴリズム
- SNSシェア・ランキング機能
- パーツの拡大縮小操作
- 元絵を「もう一度見る」機能

## 技術要件

- Phaser 4 / Vite / TypeScript（このリポジトリの標準構成、`scaffold/base-template` ベース）
- お題の元絵・パーツ（顔の輪郭、眉、目、鼻、口）はラスター画像素材を使わず、`Phaser.Graphics` によるプリミティブ図形（円・楕円・三角形・弧など）で描画する。`cjump`/`kogodrop`/`dutchcalc` と同じ方針で、素材調達が不要になり、正解配置（座標・回転角）を数値で厳密に定義できる
  - 「元絵」は正解パラメータ（各パーツの位置・回転角）から都度描画する。あらかじめ画像として保存しておく必要はない
- 輪郭は配置エリアの背景として一度だけ固定位置に描画する非インタラクティブな要素とし、ドラッグ可能なパーツ（眉2・目2・鼻1・口1の6個）とは別に扱う。採点用のオフスクリーン描画・比較にも含めない
- パーツの配置・回転は単一のドラッグ操作（`pointerdown`/`pointermove`/`pointerup`）で実装する。専用の回転ハンドルは置かない。具体的なロジック（初期実装の出発点。感触の微調整は `game-balance` で行う）:
  1. `pointerdown`: つかんだスクリーン座標を `lastPointer` として保持する。あわせて、つかんだ点のパーツローカル座標（`grabLocalOffset`）を求めて保持する（ドラッグ中ずっと固定）。その位置に掴み点マーカー（小さな円などの図形）を生成してパーツと同じコンテナに追加する（マーカー表示専用。位置・回転の計算には使わない）
  2. `pointermove`: **「掴んだ点（ホールドポイント）を直接動かし、パーツ本体はそれに引っ張られてついてくる」という考え方で更新する**
     - 目標回転角 `targetRotation` は、「直近の移動方向」から**掴んだ点自身のパーツローカル角度 `grabLocalAngle`（`atan2(grabLocalOffset.y, grabLocalOffset.x)`。ドラッグ中は `grabLocalOffset` 同様に固定値）を差し引いた値**とする（`targetRotation = atan2(dy, dx) - grabLocalAngle`）。移動量が一定のしきい値未満なら `targetRotation` は現在の回転角のまま変えない（静止中に回転がふらつくのを防ぐため）
     - `grabLocalAngle` を差し引く理由（不採用案6参照）: 回転角そのものを移動方向に一致させると、移動方向を向くのはパーツの**ローカル+x軸**であって「掴んだ点」ではない。掴んだ点のローカル角度が0に近い（パーツの+x軸付近を掴んでいる）ときだけ偶然「掴んだ点が先頭、本体が後ろに追従する」ように見え、掴んだ点のローカル角度が0から離れる（特に180°に近い、つまり+x軸の反対側を掴んだ）ときは、掴んだ点がむしろ移動方向の**逆**を向いてしまい、パーツ本体（中心）がポインタより前に出る＝「ポインタを通じてパーツを押しているように見える」逆転現象が起きる。`grabLocalAngle` を差し引いて回転角を求めることで、掴んだ点がどこであっても、掴んだ点自身が常に移動方向を向くようになり、本体は常にその後ろに追従する
     - 実際の回転角は `targetRotation` に一気に合わせず、現在の回転角から一定の割合（`ROTATION_LERP_FACTOR` を移動量に応じて調整した「実効lerp係数」。詳細は次項）だけ近づける（線形補間・lerp）。これにより回転は毎フレーム少しずつ「追いつく」動きになる
     - **実効lerp係数（移動量に応じたスケーリング）**: `targetRotation` は1フレームの移動ベクトル（`lastPointer -> pointer`）だけから求まるため、移動量が小さいほどそのベクトルの向きは入力のわずかなピクセル単位のブレ（マウス/タッチのサンプリング誤差）に対して敏感になり、ゆっくりドラッグしているときほど `targetRotation` 自体が不安定に振れる。この不安定な目標値に対して常に同じ割合（`ROTATION_LERP_FACTOR`）で追従すると、ゆっくり動かしたときの方が向きが激しく変わって見えてしまう。これを避けるため、実際に使う lerp 係数を移動量に応じてスケーリングする: `speedRatio = clamp(moveDistance / CONFIDENT_ROTATION_DISTANCE, 0, 1)`、`実効lerp係数 = ROTATION_LERP_FACTOR * speedRatio`。移動量が `CONFIDENT_ROTATION_DISTANCE`（目安10px/フレーム）以上なら通常通り全開の `ROTATION_LERP_FACTOR` で追従し（速いドラッグの感触は変えない）、`ROTATION_UPDATE_THRESHOLD` 付近のわずかな移動では実効lerp係数がほぼ0に近くなり、ノイズの影響がほとんど回転に反映されなくなる。シミュレーションで、ゆっくり・ノイズありのドラッグ（1フレーム1〜2px、方向に±1px程度のブレを含む）でのフレーム間最大回転変化量が約7.9°→約1.8°に減少し、速いドラッグ（1フレーム10px以上）の挙動は変化しないことを確認した
     - 新しい回転角が決まったら、`grabLocalOffset` にその回転を適用した位置（＝ホールドポイントの位置）が**ちょうど今回のポインタ位置に一致する**ように、パーツ中心位置を逆算する（ホールドポイントは常にポインタに完全一致させる。中心位置はホールドポイントの位置と回転から決まる従属変数）
     - 最後に `lastPointer` を今回のポインタ位置で更新する（次フレームの `targetRotation` 計算の基準にする）
     - 回転が毎フレーム少しずつしか変化しないため、そこから逆算される中心位置の変化量も自然に小さく収まり、瞬間移動は起きない（回転が一気に変わらないことが、位置の連続性も保証する）
     - この方式なら「ポインタ＝ホールドポイントを動かしていて、パーツ本体はそれに引っ張られて追従する」という感触になり、なおかつポインタをぐりぐり動かせば目標角度が変わり続けるので向きの調整も引き続き可能
     - （経緯・不採用案1）「掴んだ瞬間のパーツ中心」を固定点として、そこから現在のポインタへの向きを回転角にする案 → 一直線にドラッグしても角度が変わり続け「引っ張る方向と無関係に回転する」不自然な挙動になり不採用
     - （経緯・不採用案2）「ドラッグ開始点から現在のポインタへの向き」を回転角にする案 → 最終的な位置だけで回転が一意に決まってしまい、ドラッグ中に向きを作り直せない（ぐりぐり動かして調整できない）ため不採用
     - （経緯・不採用案3）「直近の移動方向」を回転角にしつつ、「掴んだ点を常にポインタ直下に置く」制約（`grabLocalOffset` を回転させてポインタに合わせて中心位置を逆算する）も維持する案 → 回転が急変するたびに中心位置が不連続に瞬間移動してしまい不採用
     - （経緯・不採用案4）不採用案3の反省から「位置は1:1平行移動、回転だけ直近の移動方向を参照」と位置・回転を完全に分離する案を採用していた（瞬間移動は解消した）が、実際に触ると「パーツ本体を直接動かしていて、掴み点はただの飾り」という感触になってしまい、「掴んだ点を動かしていて、パーツはそれに引っ張られてついてくる」という意図した感触と逆だった
     - （経緯・不採用案5）不採用案4の反省から「`targetRotation` をパーツの現在の中心からポインタへの向きとする」案（ホールドポイントは常にポインタに一致させたまま）を採用していたが、この「現在の中心」自体が「ホールドポイントがポインタに一致する」という制約から逆算される値であるため自己参照になっており、ポインタが静止していても `targetRotation` が現在の回転より常に一定角度（＝ホールドポイントのパーツ内での局所的な向き）だけ先の値になり続け、その差分をlerpで埋めようとして**毎フレーム同じ量だけ回転し続ける（＝クルクル回り続ける）**不具合があり不採用。目標角度の基準を、自己参照する「現在の中心」ではなく独立した値である「直近の移動方向」（`lastPointer` 基準）に変更した現在の方式で、この自己参照を断ち切った
     - （経緯・不採用案6）不採用案5の修正（`lastPointer` 基準への変更）で「クルクル回り続ける」問題は解消したが、実際に触ると「ポインタを引っ張るというよりも、ポインタを通じてパーツを押す感じ」になる場合があった。原因は `targetRotation` を移動方向そのもの（`atan2(dy, dx)`）としていたこと — これは移動方向を向かせる対象を暗黙にパーツの**ローカル+x軸**にしてしまっており、「掴んだ点」自身の向きではなかった。掴んだ点のローカル角度 `grabLocalAngle` がたまたま0に近い（パーツの+x軸付近を掴んだ）場合だけ「掴んだ点が先頭」に見え、`grabLocalAngle` が0から離れる（特に180°付近、+x軸の反対側を掴んだ）場合は掴んだ点が移動方向の逆を向き、パーツ本体がポインタより前に出る＝押しているように見える逆転が発生することをシミュレーションで確認した（`grabLocalOffset=(-20,2)` で直線ドラッグすると、中心がポインタの前方に張り付き続けることを確認）。`targetRotation = atan2(dy, dx) - grabLocalAngle` として「掴んだ点自身」を移動方向に向かせるよう修正し、不採用とした
  3. `pointerup`: 離した位置が配置エリア内かトレイ領域内かで分岐する
     - 配置エリア内: その時点の位置・回転で確定し、そのパーツの Input を無効化する（以後 `pointerdown` を受け付けない）
     - トレイ領域内（または未確定のまま画面外など想定外の場所で離した場合）: 確定せず、離した位置・角度のまま Input は有効に保つ（トレイの初期位置には戻さない）
     - いずれの場合も、掴み点マーカーを削除する
- パーツの当たり判定は**円形**とし、見た目のサイズより一回り大きい半径を取る（小さいパーツでも掴みやすくするため）。円形にしているのは、回転しても形が変わらず「当たり判定が回転にずれてついてこない」バグを構造的に避けられるため。当たり判定の円は薄く可視化し、プレイヤーが掴める範囲を見て分かるようにする
  - 実装上の注意（ハマった点）: Phaser の `Container` に `setInteractive(shape, callback)` でカスタム形状を渡す場合、コールバックに渡ってくる `(x, y)` はコンテナのローカル原点 `(0, 0)` を基準にした座標ではなく、`(半径, 半径)` 分だけずれた座標になる（`Container` の `setSize()` によるデフォルトの origin 起因）。円のヒットエリアは `new Geom.Circle(0, 0, radius)` ではなく `new Geom.Circle(radius, radius, radius)` として定義する必要がある。これに気づかず `(0, 0, radius)` のまま実装すると、中心を含めどこを掴んでも判定されない（もしくは矩形判定の場合は判定範囲全体が半分ずれる）
- ドラッグ中のパーツは `depth`（描画順）を最前面に更新する
- `Game` Scene は「元絵表示」「パーツ配置」「採点」の3フェーズを内部状態（enum等）として持ち、Scene自体は分割しない。フェーズ遷移はプレイヤー操作（「はじめる」「採点する」ボタン）がトリガーで、タイマーによる自動遷移は使わない
- 採点処理はオフスクリーン描画とピクセル比較のロジックを、Scene本体から切り離した独立関数として実装し、単体テスト可能にする。背景色と一致するピクセルを比較対象から除外する処理（ルール参照）も同様に独立関数化する
  - **採点用描画のぼかし（ルール「位置ズレへの許容度」参照）**: プレイヤー・お手本両方のオフスクリーン描画（`drawFaceOnCanvas`）に、背景塗りつぶし後・パーツ描画前に `ctx.filter = 'blur(SCORE_BLUR_RADIUS_PX px)'` を適用してから描画する（Canvas 2D 標準APIのフィルタ機能。手書きの畳み込み処理は実装しない）。`SCORE_BLUR_RADIUS_PX` は独立した定数として定義し、実測でスコア−位置ズレのカーブが急峻すぎない値に調整する（初期値の目安: 6px 前後。0px・3px・6px・9px・12pxのズレでスコアを実測し、0〜6px区間の落差が極端にならないことを確認する）。「背景のみ」の基準差分キャンバスは元々パーツを描かない一様な背景色なので、同じぼかし処理を通しても実質的に変化しない（エッジがないため）
- 点数変換（`実差分`・`基準差分` から0〜100点を求める処理）は、差分計算そのものとは別の独立関数として実装し、単体テスト可能にする（`基準差分` は引数として渡す。関数自体は「背景のみキャンバスの生成」や「お題ごとのパラメータ」を知らなくてよい）
- `Result` Scene は、プレイヤーが確定した各パーツの位置・回転（トレイに残ったパーツは現在位置のまま）を使って、`Game` Scene の採点時と同じ描画ロジック（`Phaser.Graphics`）で「プレイヤーの仕上がり」を画面中央に再描画する。正解の顔は `Game` Scene の元絵表示フェーズと同じ描画ロジック・正解パラメータを使い、小さいスケールで表示する
- 配布は静的サイト前提（`vite build`）、Node専用ランタイム機能には依存しない

## テスト観点

- ドラッグ中の位置・回転算出ロジック（`lastPointer`・現在の中心・現在の回転・`grabLocalOffset`・ポインタ位置から、新しい中心と回転角を求める関数）を独立関数として切り出し、既知の入力に対する期待値でテストする。境界値: `lastPointer` からの移動量がしきい値未満なら回転が変わらないこと、しきい値を超えたら回転が `targetRotation`（＝直近の移動方向から `grabLocalAngle` を差し引いた値）に向かって実効lerp係数の割合だけ近づくこと（一気に一致しないこと）、0度・180度・360度超えの正規化。特に、**ポインタの位置を複数フレーム変えずに関数を繰り返し呼んでも、2フレーム目以降は回転・中心位置とも変化しないこと**（「クルクル回り続ける」不具合の回帰テスト。自己参照ではなく独立した基準で目標角度を求めていることの確認）、**一直線に等速でドラッグし続けた場合、数フレームで回転が収束し、それ以上変化し続けないこと**、**新しく求めた中心位置・回転から逆算したホールドポイントの位置が、常にそのフレームのポインタ位置と一致すること**（ホールドポイントの追従精度の回帰テスト）、**1フレームあたりの回転量に上限がある（実効lerp係数以上には変化しない）ため、中心位置の変化も有界であること**（瞬間移動しないことの回帰テスト）、**`grabLocalOffset` のローカル角度が0付近だけでなく180°付近（パーツの+x軸と反対側を掴んだ場合）でも、一直線ドラッグを続けた結果パーツ中心がポインタの進行方向後方に収束すること**（「押しているように見える」逆転バグの回帰テスト。不採用案6）、および**移動量が `CONFIDENT_ROTATION_DISTANCE` 未満のときは実効lerp係数が `ROTATION_LERP_FACTOR` より小さくなり（移動量0に近いほど実効lerp係数も0に近づく）、`CONFIDENT_ROTATION_DISTANCE` 以上では通常の `ROTATION_LERP_FACTOR` と同じ実効lerp係数になること**（低速時の過敏な回転変化を抑える調整の回帰テスト）
- パーツ確定後（配置エリアでの `pointerup` 後）に同じパーツへの `pointerdown` が無視されること（再配置できないこと）
- トレイ領域で `pointerup` した場合に確定せず、離した位置・角度のまま再度ドラッグできること（初期のトレイ位置に戻らないこと。配置エリア／トレイ領域の境界値を含む）
- 背景色ピクセルを比較から除外するロジック（両方とも背景色→除外、どちらか一方でも背景色でない→比較対象、の境界値）
- 差分→点数の変換ロジック（`実差分` と `基準差分` から点数を求める関数）を独立関数として切り出し、既知の入力に対する期待値でテストする。境界値: `実差分` が0（完全一致）→100点、`実差分` が `基準差分` と等しい（何もしない場合と同じ）→0点、`実差分` が `基準差分` を上回る（何もしないより悪化）→0点にクランプされること、`基準差分` が0（お題自体に色がない特殊ケース）で0除算にならないこと
- `Game` Scene のフェーズ遷移ロジック（「元絵表示」→「配置」はボタン操作でのみ進み、時間経過では進まないこと。「配置」→「採点」も同様）
- 乱数・時刻に依存する処理があれば注入可能にしてテストで固定する
